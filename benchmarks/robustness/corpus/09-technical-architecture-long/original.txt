When a write transaction arrives at the primary coordinator node in `storage-engine-v4`, the request router first validates the schema version against the in-memory catalog before assigning a monotonically increasing 64-bit commit timestamp. If the incoming payload references a partition that is currently undergoing background compaction, the coordinator does not block the caller; instead, it appends the delta record to the write-ahead log (`wal.segment.004`) and schedules an asynchronous merge task once the active compaction window closes. This two-phase write path keeps 99th-percentile write latency below 4.2 ms under sustained loads of 18,000 requests per second across our three availability zones in production.

However, operators must account for replica lag when reading from secondary followers immediately after a bulk schema migration. Because secondary nodes replay write-ahead log segments in 64 MB batches every 250 ms, a client that issues a read-after-write query without specifying a minimum commit timestamp (`min_commit_ts`) may observe stale rows for up to 500 ms during peak compaction windows. To prevent stale reads on critical financial ledgers, callers should pass `--consistency=quorum` on the read request or attach the commit token returned by the preceding write response so the follower waits for log catch-up.

During the 12 August 2026 failover drill in `ap-south-1`, we verified that fencing tokens prevented split-brain writes when the primary network interface dropped 40% of outbound packets for 19 seconds. The lease manager revoked the old primary's epoch at t = 6.0 seconds, promoted Follower 2 at t = 6.4 seconds, and rejected three late write batches carrying stale epoch IDs (`epoch < 1042`) before they could touch disk. No committed transactions were lost during the transition, client retry queues drained within 8.1 seconds after promotion, and full three-node quorum resumed within 22.5 seconds of interface recovery.
